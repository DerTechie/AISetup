# 2026-05-22 — n8n standup on the NAS

The next infra phase is **automation via n8n**. Decision: stand it up now, keep
the scope to "running and able to talk to the gateway," and build actual
workflows in the UI later. Three things are worth recording — two reversals of
earlier decisions, and a debugging lesson that fell out of the first test call.

## Reversal 1: n8n runs on the NAS, not the t640

The Langfuse phase deliberately parked n8n on the HP t640, reasoning that NAS RAM
should be reserved for ClickHouse and that n8n's I/O-bound profile fits a weak
always-on thin client. That reasoning still holds in the abstract — but for
*getting started* it added a second host to provision for no immediate benefit.

So n8n goes on the NAS for now. Its footprint is small, it sits next to the
gateway it calls, and it's one less machine to manage. The tradeoff is explicit
and cheap to unwind: if NAS RAM ever gets tight against Langfuse/ClickHouse, n8n
is the easiest thing to relocate to the t640 later. Starting on the NAS is not a
commitment to staying there.

## Reversal 2: TrueNAS community app, not a Dockge compose stack

Every other NAS service — the LiteLLM gateway, Langfuse, the metrics stack — is a
committed `docker-compose.yml` pasted into Dockge. n8n breaks that pattern: it's
installed as the **community / TrueCharts app** through the TrueNAS app wizard.

Why diverge: simpler install and updates, and there's a maintained chart. What we
give up: the config no longer lives in a committed compose file — it's in the app
wizard — so the repo artifact becomes a *documented* install spec
(`nas/n8n/README.md`) rather than a stack file. The known risk is TrueCharts'
history of catalog churn/deprecation; the documented fallback if the chart goes
away is a TrueNAS **Custom App** with a committed compose YAML, which lands us
back near the Dockge pattern.

Settings as deployed: exposed on `:30109` (LAN-only, `http://10.63.0.2:30109`),
data on a NAS pool dataset (not publicly exposed; covered by TrueNAS snapshots, so
snapshots are the backup), and `N8N_ENCRYPTION_KEY` set to a known personal
password recorded out-of-band — never in the repo. Losing that key orphans every
stored credential, so it has to survive a redeploy.

## The lesson: a silent fallback masked a GPT-5 quirk

The first n8n call selected route `main` but the Langfuse trace showed the answer
came from local `qwen3.6:27b`, not cloud gpt-5-mini. It looked like a
wrong-model bug. It wasn't.

Root cause: the **GPT-5 family rejects `max_tokens < 16`** (`max_output_tokens
integer_below_min_value`, 400 from the provider — and because GPT-5 spends tokens
on reasoning before output, even 16 is tight). The n8n node sent a small
`max_tokens`. On that 400, LiteLLM retried twice, then applied the configured
`fallbacks: [{"main": ["private"]}]` and served local qwen with a **200 OK and no
client-visible error**.

The diagnosis is the interesting part, because two clues misled:

- A direct `deep` test *also* fell back — to its gemini fallback — which pointed
  at "OpenRouter is down." But gemini has no `max_tokens` floor, so its fallback
  *succeeded*; that success is exactly why the gemini path worked while the two
  OpenAI-on-OpenRouter routes didn't. The common factor wasn't OpenRouter, it was
  GPT-5.
- Budget was the other red herring. `/spend/logs` showed `main` had spent
  $0.0037 of its $50 cap — nowhere near it — which ruled the cap out cleanly.

What actually surfaced the truth: the gateway's `GET /health` (master key), which
reports per-model `unhealthy_endpoints` with the real upstream error instead of
the masked fallback. With `max_tokens=100`, `main` returned real gpt-5-mini.

Two takeaways:

1. **Practical fix:** set `max_tokens` generously (≥256) in n8n LLM nodes while a
   GPT-5 route is in play. The gateway already ceilings it at 8000.
2. **Structural realization:** the `main → private` fallback is silent *by design*
   ("never die"). That means **any** error on `main` — not just the budget cap —
   quietly downgrades cloud→local with a 200. When output looks dumber than it
   should, suspect a masked fallback and check the trace's `Model` field. This is
   another argument for the parked model re-pick: moving `main` off the GPT-5
   family removes this footgun entirely.

## Scope and what's next

In scope here: n8n running, persistent, LAN-only, verified able to call the
gateway (already round-tripped — trace tagged `User-Agent: n8n`). Out of scope:
all business automations, the €100-cap alert, webhook/public-URL config, nginx
fronting — built in the UI or in later specs.

Parked next: add a **tool-use / agentic reliability** data point to the `pricing/`
tracker, then re-pick `main` and `deep`. Today's price-vs-quality snapshot already
shows both cloud routes are dominated (`deep`=gpt-5 at AA 44.6 scores *below* its
own gemini-3.1-pro fallback at 57.2; `main`=gpt-5-mini is beaten on price and
intelligence by deepseek-v4-flash) — but the every-turn `main` driver has to be
chosen on tool-use reliability and latency, which the intelligence index doesn't
capture.
